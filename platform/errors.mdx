Every failure from Manifold AI and from every Tristack CPaaS channel answers with the same
JSON envelope, so one handler covers the whole API.

```json
{
  "error": "The wallet balance cannot cover the estimated cost of this request.",
  "code": "insufficient_balance"
}
```

- `error` is a sentence written for a human reading a log. Its wording can change, so never
  match on it.
- `code` is a stable `snake_case` identifier. Branch on this.
- `code` is omitted where the status alone is unambiguous, so read it defensively.

Two fields ride along on specific failures:

| Extra field | Appears on |
|---|---|
| `requiredPaise` | `402 insufficient_balance`, holding what this request needed reserved |
| `availablePaise`, `heldPaise` | `402 insufficient_balance`. `heldPaise` is what other in-flight requests have reserved, so you can tell an empty wallet from a fully reserved one |
| `partial_output` fields | `422 output_truncated` carries `content`, `usage` and `cost` alongside the error |
| `fields` | Validation failures, as an object keyed by field name with a sentence each |

## What each status means here

| Status | Meaning on this API |
|---|---|
| `200` | Done. Manifold returns the completion; the dashboard API returns the resource |
| `202` | Accepted, not finished: a Voice job whose calls have not been dialed yet, an Email send or batch the provider has accepted, or a Manifold embedding job still running |
| `400` | The request is wrong. Nothing was charged. Retrying it unchanged fails the same way |
| `401` | The credential is not usable: an API key that is missing, unknown, revoked or on an archived project, a dashboard session that has expired or whose account has been disabled, or a top-up session permit that is none of ours |
| `402` | The wallet cannot cover the estimate. Checked before any provider is called |
| `403` | The credential is fine, but this is not permitted: an account Tristack has disabled, a product switch, a key's scopes, an allowlist, or a gate a payment has to clear first |
| `404` | Not yours or not there. Another account's resource answers exactly like a missing one |
| `410` | It existed and is gone: a Voice recording whose stored file is missing, or a top-up session permit that is spent or out of time |
| `409` | An `Idempotency-Key` conflict: an earlier request with the same key is still running |
| `422` | The request was understood but could not be completed as asked: an `Idempotency-Key` reused for a different body, or output truncated before it satisfied a format contract |
| `429` | Throttled. From the model provider, from a CPaaS channel's own send limits, or from the rate limiter on the dashboard API's sign-in routes |
| `502` | A provider failed. Any wallet hold is released in full, so it cost nothing |
| `503` | A product, a channel or a payment feature is switched off or half-configured on the deployment. Not your request |

<Note>
  A `404` for a resource that belongs to another account is deliberate and not a bug. Telling
  you "this exists but is not yours" would confirm the existence of another tenant's job,
  recording or project to anyone guessing ids.
</Note>

## Every documented code

| `code` | Status | Product | What happened | What to do |
|---|:---:|---|---|---|
| `invalid_api_key` | 401 | All | Missing, malformed, unknown or revoked key. Unknown and revoked answer identically, so a leaked token cannot be confirmed as real | Check the header spelling and the value. If it was revoked, create a new key |
| `account_disabled` | 403 | All | Tristack has disabled the account that owns the key. Every key the account owns is refused, before the project and product checks, so this is the answer even on an archived project. The dashboard refuses the account's sign-in the same way | Write to hello@tristack.tech. A new key will not help: it belongs to the same account |
| `insufficient_scope` | 403 | All | The key is real but was not granted this capability. `requiredScope` names the one it needs | Create a key with that scope. Scopes cannot be changed after creation |
| `project_archived` | 401 | All | The key's project is archived. Checked before any product gate. Voice jobs already queued on the project stop before their next call: see [failures that are not status codes](#failures-that-are-not-status-codes) | Unarchive the project, or use a key from an active one |
| `invalid_request` | 400 | All | Shape or limit failure. `error` says which, and `fields` may name them | Fix the payload. Watch the casing: Manifold is `snake_case`, Tristack CPaaS is `camelCase` |
| `insufficient_balance` | 402 | All | The balance cannot cover the estimated hold. `requiredPaise` is included. Checked before any provider call | Top up, then retry. Nothing was spent |
| `manifold_disabled` | 403 | Manifold | Manifold is not switched on for this project | Turn the switch on. It applies to the next request, with no new key |
| `unsupported_field` | 400 | Manifold, SMS | The body carried a top-level field this endpoint does not accept. It is refused rather than ignored, so nothing is billed for an answer to a request that was not the one you sent. `error` names the field and suggests a near match | Remove the field, or fix the spelling |
| `unknown_model` | 400 | Manifold | `model` is neither a known alias nor a catalog model id, or it is one the platform cannot serve. Both answer identically | Copy an alias from `GET /v1/manifold/models`, which lists exactly what this key can call |
| `model_not_allowed` | 403 | Manifold | The model is real and servable, but this project's allowlist does not carry it. Refused before the hold | Add the alias under the project's model settings, or call one that is on the list |
| `provider_rejected` | 400 | Manifold | The model provider refused the request, for example an image sent to a model without vision | Fix the request. Check the model accepts what you sent |

| `provider_throttled` | 429 | Manifold | The model provider is throttling. Not a Tristack rate limit | Retry with exponential backoff and jitter |
| `provider_error` | 502 | All | Any other provider failure: the model provider, the mail provider, the SMS operator or the number provider. | `model_kind_mismatch` | 400 | Manifold | The alias is real but belongs to the other surface: an embedding model sent to `/v1/manifold/messages`, or a chat model sent to `/v1/manifold/embeddings` | Send it to the route that serves it. `GET /v1/manifold/models` reports each alias's `kind` |
| `invalid_input` | 400 | Manifold | `input` on an embeddings request is missing, empty, or neither a string nor an array | Send a non-empty string, or an array of them |
| `input_too_large` | 400 | Manifold | Beyond 2048 inputs, 8 MB in one request, or the model's own shorter input limit. Refused before the hold | Split the batch. Nothing was charged |
| `unsupported_input_modality` | 400 | Manifold | Video or audio sent to `/v1/manifold/embeddings`, which is request-and-reply only | Submit it to `POST /v1/manifold/embeddings/jobs` instead |
| `embedding_job_not_found` | 404 | Manifold | No such embedding job. Another project's job answers identically | Check the id came from this project |
| `embedding_job_timeout` | n/a | Manifold | Not a response code. A video or audio job that did not finish within 90 minutes is failed with this on the job itself, and the reservation is returned in full | Resubmit, or split a very long file. Nothing was charged |
| `output_truncated` | 422 | Manifold | Generation hit `max_tokens` before the answer satisfied the format you asked for. Default when `response_format` or a forced `tool_choice` was sent; a truncated prose answer is still a `200`. The body carries the partial `content`, `usage` and `cost`, because the tokens were spent | Raise `max_tokens`, or send `on_truncation: "return"` to receive the partial output as a `200` |
| `invalid_idempotency_key` | 400 | Manifold | The `Idempotency-Key` header was empty or longer than 255 characters. Refused before anything runs | Send a key of 1 to 255 characters |
| `idempotency_in_progress` | 409 | Manifold | An earlier request with this key is still running. Its `requestId` is included | Wait for it to finish, then retry with the same key to receive its result. Do not send a new key: that buys a second answer |
| `idempotency_key_reused` | 422 | Manifold | This key was already used for a request with a different body. Replaying the stored answer would answer a question you did not ask, so it is refused | Use a new key. One key means one request |
| `idempotency_replay_failed` | 409 | Manifold | The first request's result could not be replayed | Send support the `mfr_…` id from the response |
| `relay_voice_disabled` | 403 | Voice | Voice is not switched on for this project | Turn the switch on. The first time on a project costs Rs 200 |
| `relay_voice_unavailable` | 503 | Voice | The operator switched the product off, or the deployment is missing a public base URL, call credentials, speech credentials or any usable voice. Half-configured is refused rather than half-served | Nothing you can fix in the request. Contact support |
| `compliance_required` | 403 | Voice | The account has no accepted business verification, so it cannot rent a number | Submit your incorporation and GST certificates. Once per account, not per project |
| `compliance_pending` | 409 | Voice | A verification is already under review | Wait for the outcome. A person reviews it, normally within a few days |
| `compliance_exists` | 409 | Voice | The account is already verified | Nothing to do. Go straight to searching for a number |

| `unsupported_document_type` | 400 | Voice | A verification document is not a PDF, JPEG or PNG | Convert it and submit again |
| `number_unavailable` | 409 | Voice | The number was taken between your search and your purchase | Search again and pick another. The wallet hold is released, so nothing was charged |

| `audio_not_found` | 404 | Voice | No such recording on this account. Another account's id answers identically | Send `text` instead and keep the new `audioId` |
| `invalid_speed` | 400 | Voice | `speed` is outside 0.7 to 1.2. Refused rather than clamped | Send a value in range, or omit it to use the project's tempo |
| `job_not_found` | 404 | Voice | No job with that id on this account. Another account's job answers identically | Check the `jobId` came from one of your own sends |
| `missing_data_field` | 400 | Voice | A business verification left out a `required` field. `documentType` and `field` name it | Add the field and submit again |
| `relay_email_disabled` | 403 | Email | Email is not switched on for this project | Turn the switch on in the project's Email tab, under CPaaS. Enabling costs nothing |

| `domain_limit_reached` | 409 | Email | This project already holds 25 domains, counting unverified ones | Remove one you are not using. Unverified claims expire after seven days |
| `domain_not_found` | 404 | Email | This project does not hold that domain. A domain held by someone else answers identically | Check the spelling against `GET /v1/relay/email/domains` |
| `invalid_address` | 400 | Email | An address in `from`, `to`, `cc`, `bcc` or `replyTo` did not parse | Correct it. `error` names what failed |

| `too_many_messages` | 400 | Email | A batch of more than 500 messages | Split it |

<Accordion title="Codes from the dashboard API" icon="gauge">
  These come from the account and wallet routes under `/api/v1`, which use your session token
  rather than an API key. They never appear on `/v1/manifold` or `/v1/relay`, though
  `below_minimum_topup` and `razorpay_disabled` also answer on `/v1/wallet`, where the same
  two rules apply to an embedded top-up.

  - `email_unverified` (403): topping up requires a verified email address. Resend the link
    from the dashboard.
  - `below_minimum_topup` (400): the minimum is Rs 100 (`10000` paise).
  - `razorpay_disabled` (503): payments are not configured on this deployment.
  - `invalid_range` (400): `from` is later than `to` on the usage endpoint.
  - `invalid_status` (400): the usage `status` filter is not one of `all`, `succeeded`,
    `failed`, `provider_error`.
  - `invalid_request` (400): a validation failure, with `fields` naming what to fix.
  - `account_disabled` (403 at sign-in, 401 on a session): Tristack has disabled the account.
    Signing in with the right password or with Google answers `403`, a password reset link
    answers `403` when it is used, and a session token issued before the disable answers `401`
    with this code on its next request. Write to hello@tristack.tech.
</Accordion>

## Wallet and top-up codes

These come off the money surfaces rather than off a product: minting a top-up window from
your own app, the hosted window itself, automatic top-ups, and the billing profile every
payment is judged against. Same envelope, same rule about `code`.
[Automatic top-ups →](/platform/auto-topup)

| `code` | Status | Surface | What happened | What to do |
|---|:---:|---|---|---|
| `wallet_topup_disabled` | 403 | Embedded top-up | The project's **allow this project's keys to open the top-up window** switch is off. Refused before any session exists | Turn it on in the project's settings. It applies to the next mint, with no new key |
| `origin_not_allowed` | 403 | Embedded top-up | The `origin` you sent is not on the project's allowed-origins list, or is not a usable origin at all. Both answer identically | Add the exact origin (scheme, host and port, no path) in the project's settings. The usual cause is a forgotten entry, not a typo in the code |
| `account_owner_unverified` | 403 | Embedded top-up | The account owner's email address is not verified. This is the API-key equivalent of the check the dashboard applies before it takes a payment | Verify the owner's address from the dashboard, then mint again |
| `invalid_return_url` | 400 | Embedded top-up | Redirect mode with no `returnUrl`, or one that does not sit on `origin` | Send a `returnUrl` on the same origin. The binding is what stops it becoming an open redirect wearing a Tristack address |
| `topup_session_invalid` | 401 | Hosted window | The permit is missing, unknown, or not one of ours | Mint a fresh session from your backend. Never retry the same URL |
| `topup_session_expired` | 410 | Hosted window | Fifteen minutes passed with no payment, or a paid window sat open past its confirmation grace | Mint a fresh session |
| `topup_session_used` | 410 | Hosted window | The permit already opened an order. A reloaded window, or a stale URL out of browser history, lands here | Mint a fresh session |
| `auto_topup_unavailable` | 503 | Auto top-up | Recurring payments are not available on this deployment. Answered by the two calls that arm the arrangement: adding a payment method and switching it on | Nothing you can fix. Manual top-ups are unaffected |
| `no_mandate` | 502 or 400 | Auto top-up | `502` after registration: the payment succeeded and **the wallet was credited**, but the bank returned no usable mandate. `400` on switching it on: there is no saved payment method to arm | Register a payment method again, or use a different card. Never read the `502` as a failed payment |
| `invalid_contact` | 400 | Auto top-up | Your billing profile carries no mobile number, and a bank will not authorise a standing instruction for a customer it cannot reach | Add a mobile number to the profile, then set the payment method up again |
| `billing_profile_incomplete` | 403 | Any payment | The account has no usable billing profile, so it may not pay at all. Checked on every path money can start: the dashboard, an embedded window, mandate registration and the unattended charge | Complete the billing details on your profile in the dashboard |
| `pan_required` | 403 | Any payment | The profile is complete, but this single payment is above Rs 50,000 and no PAN is on file. Strictly above, so exactly Rs 50,000 needs none | Add a PAN to the profile, or pay a smaller amount |
| `invalid_billing_profile` | 400 | Billing profile | Saving the profile failed one of its rules. `error` names which, for example a GSTIN whose embedded PAN disagrees with the PAN given | Fix the field named and save again |

The last three are the billing identity a payment is admitted on rather than anything about
the request. What makes a profile complete, and why exactly Rs 50,000 needs no PAN, is on its
own page.
[Billing profile →](/platform/billing-profile)

<Note>
  The three session codes are the reason `410` is not a Voice recording story alone.
  They reach your app as a window telling the payer it cannot continue, not as a response to
  a call your backend made, and all three mean one thing: the permit is spent, and the fix is
  a new one.
  [Top up from your own app →](/platform/embedded-topup)
</Note>

## What an error costs

Almost nothing, by design. The order of checks is deliberate:

<Steps>
  <Step title="Authentication and product gates">
    `invalid_api_key`, `account_disabled`, `project_archived`, `insufficient_scope`, every
    product and channel switch (`manifold_disabled`, `relay_voice_disabled`,
    `relay_email_disabled`, `relay_whatsapp_disabled`, `relay_sms_disabled`) and every
    `..._unavailable` code are decided before any money is touched.
  </Step>
  <Step title="Validation and allowlists">
    `invalid_request`, `unknown_model`, `model_not_allowed`, `invalid_phone_number`,
    `unknown_voice`, `invalid_audio_id` and `invalid_callback_url` are all refused before the
    wallet hold. So are Email's `from_domain_not_verified`, `invalid_address`,
    `no_recipients`, `empty_body`, `header_injection`, `subject_too_long` and
    `message_too_large`, and `rate_limited` is refused before the hold too.
  </Step>
  <Step title="The balance check">
    `insufficient_balance` is the hold itself failing. No provider has been contacted.
  </Step>
  <Step title="Provider failures">
    Everything that reaches a provider and fails (`provider_error`, `model_access_denied`,
    every `speech_*` code, `text_rejected`, `voice_unavailable`) releases the hold in full.
  </Step>
</Steps>

<Warning>
  The one exception is a **client abort mid-stream** on Manifold. If you disconnect while
  tokens are arriving, the request settles against what was already generated, using the
  provider's usage when it reported any and an estimate from the streamed characters
  otherwise, never above the hold. It is recorded as a failure with the code `client_aborted`
  and it is real money, because the tokens were really generated.
</Warning>

## Rate limits

| Surface | Limit | Answer |
|---|---|---|
| `/v1/manifold/*` and `/v1/relay/voice` | None from Tristack | A `429` here is `provider_throttled` from the model provider |
| `/v1/relay/email` | 5 per second per project, plus a platform ceiling | `429` with `rate_limited` and a `Retry-After` header |
| Sign-in and account recovery: `/api/v1/account/register`, `/login`, `/google-login`, `/forgot-password`, `/reset-password`, `/verify-email` and `/resend-verification` | 10 per minute per IP, plus 120 per minute across the process | `429` with an empty body |
| `/api/v1/contact` | 5 per minute per IP, plus 60 per minute across the process | `429` with an empty body |

<Note>
  Manifold and Voice are not throttled on purpose: your wallet is the limit. Email is the
  exception, because email sending is rate-limited to protect deliverability, and SMS and
  WhatsApp hold each project and each recipient to send limits of their own (`rate_limited`,
  `recipient_rate_limited`).

  The rest of the dashboard API, including the signed-in account routes such as the profile,
  is not rate limited.

  Either way, a retry loop against a `402` or a `403` will spin as fast as you can send,
  writing nothing but rejections. Back off on your side.
</Note>

An empty-body `429` is the only response on the API without the JSON envelope. Unknown routes
under `/api/` or `/v1/` answer `404 { "error": "Unknown API route" }` with no `code`, rather
than serving the dashboard's HTML.

## Failures that are not status codes

A Voice request or a Manifold embedding job can be accepted with `202` and still go wrong
later, so those failures are read from the job rather than from a status code.

- **`error` on a Voice job**: `audio_unavailable` (the recording vanished before dialing),
  `interrupted` (the service restarted mid-job; nothing is redialed, and the calls were free),
  `internal_error`, `account_disabled` or `project_archived`.
- **`account_disabled` and `project_archived` on a Voice job**: the account was disabled, or
  the project archived, after the job was accepted. The job checks before every call it
  places, so the calls not yet placed end `Cancelled`, calls already ringing finish, and the
  job ends `Failed` with that code. It settles like any other finish: the speech charge stands,
  because the recording was made, and the calls cost nothing. The key can no longer read the
  job back once that has happened, so a `callbackUrl` is how you learn of it.
  [Job status →](/api-reference/relay-voice/job)
- **`error` on a call**: why that one number failed, alongside its status.
- **Call statuses that are not errors at all**: `Busy`, `NoAnswer` and `Cancelled` are normal
  outcomes of telephoning people. None of them is billed. A job status of `Completed` means
  every call reached a terminal state, not that anyone answered.
- **`account_disabled` on an embedding job**: a video or audio job of an account that was
  disabled while it ran ends `failed` with this code at its next check. No vectors are
  returned, nothing is charged and the reservation is released in full. Archiving a project
  does not stop an embedding job. [Embeddings →](/api-reference/manifold/embeddings)

## Handling them

<CodeGroup>
```python Python
# pip install requests
import os

import requests

response = requests.post(
    "https://api.tristack.tech/v1/manifold/messages",
    headers={"Authorization": f"Bearer {os.environ['TRISTACK_API_KEY']}"},
    json={
        "model": "nova-micro",
        "max_tokens": 64,
        "messages": [{"role": "user", "content": "Say hello from Tristack."}],
    },
    timeout=60,
)

if response.ok:
    print(response.json()["content"][0]["text"])
else:
    # raise_for_status() would throw the body away, and the body is where `code` lives.
    failure = response.json()
    code = failure.get("code", "")
    print(f"{response.status_code} {code}: {failure['error']}")

    if code == "insufficient_balance":
        print(f"this call needed {failure['requiredPaise']} paise reserved")
    elif code == "provider_throttled":
        print("retry with backoff")
    elif code in ("model_not_allowed", "manifold_disabled"):
        print("fix the project settings, not the request")
```

// Node 18 or newer, no dependencies. Save as .mjs, or set "type": "module".
const response = await fetch("https://api.tristack.tech/v1/relay/voice", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.TRISTACK_API_KEY}`,
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    to: ["+91XXXXXXXXXX"],
    text: "Your delivery arrives between 4 and 6 today.",
  }),
});

if (!response.ok) {
  const failure = await response.json();
  console.error(`${response.status} ${failure.code}: ${failure.error}`);

  if (failure.code === "insufficient_balance") {
    console.error(`needed ${failure.requiredPaise} paise`);
  }
} else {
  const job = await response.json();

  console.log(job.jobId, job.status, job.estimatedCostPaise);
}
