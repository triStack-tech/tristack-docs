Manifold and Relay Voice are separate products. They share an account, a wallet and a key
scheme, and nothing else. That shared plumbing is what makes them look like one product with
two modes, so this page draws the line precisely.

## Side by side

| | Manifold | Relay Voice |
|---|---|---|
| **Endpoint** | `POST /v1/manifold/messages` | `POST /v1/relay/voice` |
| **Catalog** | `GET /v1/manifold/models` | `GET /v1/relay/voice/voices` |
| **You send** | Messages, a model alias, `max_tokens` | Indian mobile numbers, and `text` or an `audioId` |
| **You get** | Generated text, in the response or as SSE | `202` with a `jobId`, then per-call status |
| **Timing** | Synchronous. The answer is the response | Asynchronous. Calls are dialed in the background, 3 at a time process-wide |
| **JSON casing** | `snake_case` on the wire (`max_tokens`, `stop_sequences`) | `camelCase` on the wire (`audioId`, `callbackUrl`) |
| **Charged for** | Every token in and out, at the model's rate | Every **answered** call (40 paise), plus 3 paise per character of newly synthesized speech |
| **Charged nothing for** | A request refused before the provider is called | A phone that rings out, is engaged, or is refused |
| **One-time charge** | None | Rs 200 (20000 paise) the first time Relay Voice is switched on for a project |
| **Project switch** | Manifold | Relay Voice |
| **Refused with, when off** | `403 manifold_disabled` | `403 relay_voice_disabled` |
| **Identifiers** | `mfr_…` request id | `rvj_…` job id, `rvc_…` call id, `aud_…` recording id |

<Warning>
  The casing difference is real and it bites. Manifold takes `max_tokens`; Relay Voice takes
  `callbackUrl`. Sending `maxTokens` to Manifold or `callback_url` to Relay Voice is a
  `400 invalid_request`. Manifold's shape follows the Anthropic Messages API it is modelled
  on, and Relay Voice follows the rest of the platform.
</Warning>

## Neither product feeds the other

<Note>
  **Nothing passes between them automatically.** Manifold never dials a phone, and Relay
  Voice never asks a model for anything. There is no field on either request that reaches
  across, and no setting that turns one on. To Relay Voice, text written by a model is text
  you typed.
</Note>

If you want a model to write the words and a phone to speak them, your code makes both calls
and carries the string between them. That is the whole integration:

```bash Manifold writes it, Relay Voice says it
export TRISTACK_API_KEY="tsk_live_your_key_here"

# 1. Ask a model for the sentence.
TEXT=$(curl -s https://api.tristack.tech/v1/manifold/messages \
  -H "Authorization: Bearer $TRISTACK_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"nova-micro","max_tokens":120,
       "messages":[{"role":"user",
                    "content":"One sentence telling a customer their order ships today. No greeting."}]}' \
  | jq -r '.content[0].text')

# 2. Phone it to somebody. jq -n builds the JSON so quotes in TEXT cannot break it.
curl -s https://api.tristack.tech/v1/relay/voice \
  -H "Authorization: Bearer $TRISTACK_API_KEY" \
  -H "Content-Type: application/json" \
  -d "$(jq -n --arg text "$TEXT" '{to:["+91XXXXXXXXXX"], text:$text}')"
```

That script needs `jq`, and it needs **both** switches on for the project the key belongs to.
Cap `max_tokens` low enough that the answer fits Relay Voice's 1500 character limit, because
Relay Voice will refuse text longer than that rather than truncate it.

## What they actually share

<AccordionGroup>
  <Accordion title="One account, one wallet" icon="wallet">
    There is a single prepaid balance per account, in paise, and both products draw on it.
    There is no per-product balance and no per-project balance. A Manifold call and a Relay
    Voice job spend the same money, and either one can be the call that runs it out.

    Both bill hold-then-settle: an estimate is reserved before any work starts and the real
    cost is debited when the work finishes. [Wallet and billing →](/platform/wallet)
  </Accordion>

  <Accordion title="One kind of API key" icon="key">
    The same `tsk_live_…` token authenticates both, in either header form. What a key can do
    is decided entirely by the switches on its project: with both on, one key calls both
    products; with one on, the other answers `403` and nothing is charged.

    [Projects and keys →](/platform/projects-and-keys)
  </Accordion>

  <Accordion title="One error envelope" icon="triangle-exclamation">
    Every failure from either product is `{ "error": "<sentence>", "code": "<snake_case>" }`.
    Four codes are common to both: `invalid_api_key`, `project_archived`, `invalid_request`
    and `insufficient_balance`. The rest are specific to one product.

    [Every code →](/platform/errors)
  </Accordion>

  <Accordion title="One ledger and one usage report" icon="receipt">
    Wallet rows from both products sit in the same ledger, told apart by the `reference`
    field: `mfr_…` for a Manifold request, `rvj_…` for a Relay Voice job. `GET /api/v1/usage`
    reports both, with a `product=manifold|relay_voice|all` filter.

    A Relay Voice row counts calls placed and a Manifold row counts requests, so the two are
    never added into one number.
  </Accordion>
</AccordionGroup>

## What they do not share, mechanically

- **Switches.** `manifoldEnabled` and `relayVoiceEnabled` are separate fields on the project.
  Turning one on does nothing to the other, and neither is on when a project is created.
- **Catalogs.** Manifold's `GET /models` answers per key: it lists only models this project
  may call, narrowed by its allowlist, so two keys can see two different lists. Relay Voice's
  `GET /voices` is the same list for everyone on the deployment.
- **Units.** Tokens and answered calls have no exchange rate between them. A model alias
  cannot be sent to Relay Voice, and a voice alias means nothing to Manifold.
- **Failure shape.** A Manifold failure is the status code of your request. A Relay Voice
  request can succeed with `202` and then have individual calls fail hours later, which you
  read from the job or receive on a callback.
