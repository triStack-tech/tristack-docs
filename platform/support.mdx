## Getting help

Write to [support@tristack.tech](mailto:support@tristack.tech).

An answer is only as good as the detail in the question. A message saying a call failed can
only be answered with questions; a message carrying the identifiers below can be answered
with the actual record.

<Warning>
  **Never send an API key or a password.** Nobody at Tristack Technologies LLP needs either,
  and a key pasted into an email should be revoked rather than explained. The dashboard shows
  every key by prefix and last 4 characters, which is all anyone needs to work out which key
  you mean.
</Warning>

## What to include

<CardGroup cols={2}>
  <Card title="The identifier" icon="fingerprint">
    The id of the thing that went wrong. It ties your report to a wallet ledger row and a
    usage row, which is what turns "a call failed" into a specific record.
  </Card>
  <Card title="The code and the status" icon="triangle-exclamation">
    The `code` from the error envelope and the HTTP status, copied exactly. `403` with
    `model_not_allowed` and `403` with `manifold_disabled` are different problems.
  </Card>
  <Card title="The alias" icon="tag">
    The model alias for Manifold, the voice alias for Relay Voice. Behaviour differs by
    model and by voice.
  </Card>
  <Card title="Roughly when" icon="clock">
    A time and a timezone, or a UTC timestamp. Anything inside a few minutes is enough to
    find the record.
  </Card>
</CardGroup>

Which identifier depends on the product:

| Product | Send this | Where you got it |
|---|---|---|
| Manifold | `mfr_…` | `id` on the response, or `message_start.id` on a stream |
| Relay Voice | `rvj_…` | `jobId` on the `202`, and on every status read |
| Relay Voice, one number | `rvc_…` | `callId` on that entry in the job's `calls` array |
| Relay Voice, a recording | `aud_…` | `audioId` on the job |
| Either | Your own `reference` | Whatever you set on the request, echoed back |

The project id helps too, especially when the answer turns out to be a switch or an allowlist
rather than the request.

## The contact form

The form on [tristack.tech](https://tristack.tech) posts to a public endpoint,
`POST /api/v1/contact`. It takes no authentication and stores nothing: a submission becomes
an email.

<ParamField body="name" type="string" required>
  Up to 100 characters.
</ParamField>

<ParamField body="email" type="string" required>
  Up to 254 characters, and a plain address. `Name <a@b.com>` is refused; `a@b.com` is fine.
</ParamField>

<ParamField body="message" type="string" required>
  Up to 4000 characters.
</ParamField>

A success answers `200 { "message": "Thanks, we will get back to you." }`. Each field has its
own failure code: `invalid_name`, `invalid_email` and `invalid_message`, all `400`.

<Note>
  The form is protected by a browser challenge, and the challenge token is part of the
  submission. A scripted post without one answers `400 challenge_failed`, so the form is a
  form rather than a scriptable inbox. Use email instead of automating around it.
</Note>

<Warning>
  **The endpoint is rate limited**: 5 requests per minute per caller IP, with a process-wide
  backstop of 60 per minute. Over either, the answer is `429` with an empty body. It is the
  tightest limit on the API. See [rate limits](/platform/errors#rate-limits).
</Warning>

For anything about an actual call, email beats the form. The form has no place to put a
request id, and the request id is what makes the answer specific.
