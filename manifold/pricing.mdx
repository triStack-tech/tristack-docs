Manifold is metered per token against a prepaid wallet. Nothing is invoiced monthly and
nothing is charged by the request: you pay for the tokens a call actually used, at the
model's own rate, and the response tells you what that came to.

## The short version

- One **prepaid wallet per account**, shared by every project and by Relay Voice.
- Everything is an **integer in paise**. Rs 1 is `100`. No rupee floats anywhere.
- Before a call, an **estimate is held**. After it, the **real usage is settled** and the
  rest of the hold comes back.
- A failed call costs **nothing**, with exactly one exception: a stream you abort part-way.
- `cost.paise` on every response is the settled amount, not the estimate.

## What a token costs

Manifold takes the provider's own rate in USD, converts at **100 INR to the dollar**, and
adds a **10 percent margin**:

```text
costPaise = ceil(
  (inputTokens * usdPerMTokIn + outputTokens * usdPerMTokOut)
  / 1e6 * usdToInr * 100 * 1.10
)
```

`usdToInr` is 100 today and comes back at the top of
[`GET /v1/manifold/models`](/manifold/models); the second `100` turns rupees into paise, and
`1.10` is the margin. That endpoint also lists each model's rate two ways: `usdPerMTok` per
million tokens, and `paisePer1KTokens` per thousand with the margin already in it.

<Note>
  The same 10 percent is applied to the pre-flight estimate, to the settled cost **and** to
  the prices the catalog lists, all through one function in the pricing code. The catalog
  therefore cannot drift from the invoice: what you are quoted per 1000 tokens is what you
  are billed per 1000 tokens.
</Note>

Rounding up to a whole paise happens once, at the very end, so any call that used tokens
costs at least 1 paise. There is no per-request fee, no minimum billable token count, no
surcharge for images and no price difference between streamed and non-streamed calls.

## Estimate, hold, settle, release

Token usage is only known after a model has run. Charging up front would mean guessing, and
guessing means charging people wrong, so Manifold reserves money instead of taking it.

<Steps>
  <Step title="Estimate, before anything is called" icon="calculator">
    Input is estimated at **4 characters per token**, counted across `system`, every message
    and any base64 image data. Output is assumed to use **every one of your `max_tokens`**.

    ```text
    estimatedInput  = ceil(billableCharacters / 4)
    estimatedOutput = max_tokens
    holdPaise       = max(1, ceil(the cost formula on those two numbers))
    ```

    `max_tokens` defaults to **4096** when you omit it and is clamped to a cap of **65536**.
    The hold is priced on whatever value ends up applying, which is why omitting `max_tokens`
    on an expensive model reserves far more than you expect.
  </Step>

  <Step title="Hold" icon="lock">
    That estimate leaves the available balance and sits in a hold. If the balance cannot
    cover it, the call is refused with `402 insufficient_balance` and `requiredPaise` set to
    the hold. **No model runs, so a refused call costs nothing.**

    Holds overlap. Ten concurrent requests reserve ten estimates at once, so a balance that
    covers one call comfortably can still refuse the tenth.
  </Step>

  <Step title="Call" icon="paper-plane">
    Only now does the model run. It reports the real `input_tokens` and `output_tokens`,
    which are usually nothing like the estimate: 4 characters per token is a rule of thumb,
    and `max_tokens` is a ceiling rather than a prediction.
  </Step>

  <Step title="Settle and release" icon="scale-balanced">
    The **whole hold** is released back to the balance and the **real cost** is debited from
    it. The balance nets out at the remainder, and the ledger shows both movements against
    the same `mfr_...` request id.
  </Step>
</Steps>

## A worked example

One call to `nova-pro`, which the catalog lists at **0.80 USD per million input tokens** and
**3.20 USD per million output tokens**, or 8.80 and 35.20 paise per 1000 tokens with the
margin in. The request carries a 620-character system prompt and a 7,380-character user
message, and sets `max_tokens: 2048`.

### The hold

| Step | Arithmetic | Value |
|---|---|---|
| Billable characters | 620 + 7,380 | 8,000 |
| Estimated input tokens | `ceil(8000 / 4)` | 2,000 |
| Estimated output tokens | from `max_tokens` | 2,048 |
| Input part | `2000 * 0.80` | 1,600 |
| Output part | `2048 * 3.20` | 6,553.6 |
| In USD | `(1600 + 6553.6) / 1e6` | 0.0081536 |
| In rupees | `* usdToInr`, 100 | 0.81536 |
| In paise | `* 100` paise to the rupee | 81.536 |
| Plus margin | `* 1.10` | 89.6896 |
| Rounded up | `ceil` | **90 paise held** |

90 paise leave the available balance. Nothing has been spent yet.

### The response

```json
{
  "id": "mfr_4b8e17c0a9d2f6135ec70b44",
  "model": "nova-pro",
  "role": "assistant",
  "content": [{ "type": "text", "text": "..." }],
  "stop_reason": "end_turn",
  "usage": { "input_tokens": 1984, "output_tokens": 512 },
  "cost": { "paise": 36 }
}
```

The estimate guessed 2,000 input tokens and the model counted 1,984, which is 4 characters
per token doing its job on ordinary English. Output is the interesting half: 2,048 were
reserved and 512 were written, because `max_tokens` was a ceiling the model never came near.

### The settlement

| Step | Arithmetic | Value |
|---|---|---|
| Input part | `1984 * 0.80` | 1,587.2 |
| Output part | `512 * 3.20` | 1,638.4 |
| In USD | `(1587.2 + 1638.4) / 1e6` | 0.0032256 |
| In rupees | `* usdToInr`, 100 | 0.32256 |
| In paise | `* 100` paise to the rupee | 32.256 |
| Plus margin | `* 1.10` | 35.4816 |
| Rounded up | `ceil` | **36 paise charged** |

### In the ledger

Three lines, all carrying `mfr_4b8e17c0a9d2f6135ec70b44` as their reference:

| Type | Paise | Meaning |
|---|---:|---|
| `Hold` | 90 | The estimate, reserved before the call. |
| `HoldRelease` | 90 | The whole hold coming back, not the unused part. |
| `Debit` | 36 | The settled cost, taken from the returned money. |

The call cost 36 paise and the other 54 are back in the balance. **Read the `Debit` line for
what a call cost**: the release line is always the full hold, so subtracting one from the
other tells you nothing.

<Tip>
  The 54 paise gap is why a tight `max_tokens` is worth setting. It does not change the price
  of the tokens you use, but it stops the wallet reserving money for an answer you were never
  going to receive, which is what refuses the tenth concurrent request on a thin balance.
</Tip>

## When the settlement is larger than the hold

4 characters per token over-counts plain English and under-counts dense scripts, so a settled
cost above the hold is possible. Roughly 2,000 characters of Devanagari on `nova-lite` with
`max_tokens: 256` holds 2 paise, and if the reply runs to the cap it settles at 3.

When that happens the extra comes out of the balance rather than the call being refused: the
model has already run and the tokens are already spent. If the balance cannot cover the
overage, the debit is capped at what is actually there, the remainder is written off, and the
`Debit` line carries a description saying the cost was clamped. A wallet is never taken
negative.

In that one case `cost.paise` reports the full figure while the ledger shows the smaller
amount actually taken. On a funded wallet the two always agree.

## What a failure costs

| Outcome | Charge |
|---|---|
| Rejected before the hold: `invalid_api_key`, `project_archived`, `manifold_disabled`, `invalid_request`, `unknown_model`, `model_not_allowed` | 0. The wallet is never touched. |
| `insufficient_balance` | 0. The hold could not be placed, so no model ran. |
| `provider_throttled`, `provider_rejected`, `model_access_denied`, `provider_error` | 0. The hold is released in full. |
| A stream that fails mid-way with an `error` event | 0. The hold is released in full. |
| You aborted before any output arrived | 0. The hold is released in full. |
| You aborted after part of a stream arrived | Your whole input at 4 characters per token, plus the output that reached you, also at 4 characters per token and capped at `max_tokens`. |
| Success | The real token cost. |

The single exception exists so that hanging up one delta before the end is not repeatable
free inference. A provider failure is not your doing and costs you nothing; discarding output
that was generated and delivered does. [The detail is on the streaming
page](/manifold/streaming#what-an-abort-costs).

Retrying a failed call is therefore free apart from latency. Retry `429 provider_throttled`
and `502 provider_error` with backoff, without worrying about paying twice.

## Reading what you spent

  <Card title="Per call" icon="receipt">
    `cost.paise` on every response, and in the `message_delta` event of every stream. Log it
    beside the `mfr_...` id and you can attribute spend to a feature without reconciling
    anything.
  </Card>

  <Card title="Per movement" icon="list">
    The wallet ledger, one line per `Hold`, `HoldRelease` and `Debit`, each carrying the
    request id. [Wallet](/platform/wallet)
  </Card>

  <Card title="Per day, project and model" icon="chart-column">
    The usage view, which separates successes from failures. Read the two apart: a failed
    request usually carries zero tokens and zero cost, so summing them hides your failure
    rate.
  </Card>

  <Card title="Before it runs out" icon="bell">
    The wallet balance is readable from the dashboard API. Alarm on it well before zero, or
    your next call is a `402` in front of a user.
  </Card>
</CardGroup>

## Keeping the bill down

1. **Pick the smallest model that passes your own evaluation.** The catalog spans more than
   a hundredfold in price per token. Nothing else you do will come close to that.
2. **Set `max_tokens` to what you actually need.** It caps the hold and it caps runaway
   replies.
3. **Trim the system prompt.** It is charged on every single call, so cutting it once saves
   forever.
4. **Watch output-heavy work.** Output costs several times input on most models, so "make it
   shorter" often beats "send less context".
5. **Downscale images.** Image bytes become base64 characters, and those characters go
   straight into the estimate that sets your hold.
6. **Keep the balance to what the workload needs.** A prepaid wallet is a hard ceiling on
   what a leaked key can spend.
